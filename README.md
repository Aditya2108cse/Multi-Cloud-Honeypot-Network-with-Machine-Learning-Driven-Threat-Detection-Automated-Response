# MultiCloud-HoneypotNetworkwithAutomatedThreatDetectionandResponse

## Overview
This project extends deception-based detection by implementing automated threat response
across multiple cloud platforms. Honeypot alerts generated by OpenCanary are correlated
and used to trigger automated blocking of malicious IP addresses across AWS, Azure, and
GCP using native firewall controls.

The objective is to demonstrate cross-cloud containment of attackers once malicious
activity is detected.

---

## Objectives
- Automate threat response based on honeypot alerts
- Block malicious IPs across AWS, Azure, and GCP
- Correlate attacks from OpenCanary logs
- Validate enforcement using status verification scripts

## Architecture

```
Honeypots (OpenCanary)
        |
correlate_alerts.py   (threshold-based correlation, replaces Splunk SPL search)
        |
opencanary_export.tsv (IP<TAB>Cloud)
        |
block_attacker.py     (decision engine + automation, all clouds)
        |
AWS | Azure | GCP Firewalls
        |
multicloud_block_status.py (verification)
reset_all_blocks.py        (rollback, when needed)
```

## Scripts (`scripts/`)
| Script | Purpose |
|---|---|
| `correlate_alerts.py` | Reads OpenCanary's JSON log, counts events per source IP within a rolling window, and exports any IP over the threshold (default: 3 events / 15 min) to `opencanary_export.tsv`. Standalone Python equivalent of the original Splunk SPL correlation search — no Splunk required. |
| `block_attacker.py` | Reads the export TSV and blocks each IP across AWS (managed prefix list), Azure (scalable NSG rule), and GCP (per-IP firewall rule). Supports `DRY_RUN=1`. |
| `multicloud_block_status.py <ip>` | Checks whether a given IP is currently blocked on each cloud. |
| `reset_all_blocks.py` | Clears all auto-created blocks across AWS, Azure, and GCP. |
| `common.py` | Shared helpers: config loading (`/etc/auto-block.conf`), logging, CLI detection, retry-with-backoff. |

All scripts read cloud credentials/config the same way the CLIs themselves do
(`aws configure`, `az login`, `gcloud auth login`, or the `AZURE_CLIENT_ID` /
`AZURE_CLIENT_SECRET` / `AZURE_TENANT_ID` service-principal env vars), plus an
optional `/etc/auto-block.conf` file of `KEY=VALUE` lines for settings like
`AWS_PL_ID`, `AWS_REGION`, `AZURE_RG`, `AZURE_NSG`, `GCP_PROJECT_ID`.

## Automated Response Workflow
1. Honeypot (OpenCanary) detects malicious activity and logs it
2. `correlate_alerts.py` evaluates the log, flags IPs over the alert threshold, writes them to the export file
3. `block_attacker.py` reads the export and blocks the IP across all configured cloud platforms
4. `multicloud_block_status.py` confirms enforcement
5. `reset_all_blocks.py` is available to roll everything back when needed

## Validated Scenarios
- SSH brute-force attacks
- Azure to GCP lateral movement
- Cross-cloud IP blocking
- Block verification across providers

## Limitations
- CLI credential dependency
- Time-window based detection
- Requires per-cloud authentication setup

## Lessons Learned
- Importance of independent provider execution
- Credential scope challenges in automation
- Verification vs enforcement gaps
